# Semantic Search Wiring

Status: **Approved**
Last updated: 2026-08-13
Depends on: [Semantic search and ranking](06-semantic-search-ranking.md), [Transactional projection digests](13-transactional-projection-digests.md)

**Provisioning update (2026-08-13, supersedes the "downloads on first use" story below):** the open local model is now downloaded when urdira is CONFIGURED (`core:workspace_add`/`core:workspace_configure`/`core:configuration_set`), never at daemon start and never on an embed path (first query, first index). See "Configure-time model provisioning" under Decision, below.

## Decision objective

Wire `core:search_semantic`/`core:search_hybrid` end to end -- daemon maintenance job, query port, and app-level configuration -- behind a pluggable embedding provider, so both operations answer real candidates from a real, incrementally maintained vector index instead of throwing `core:unknown_call`/returning an empty stream forever.

## Context

Decision 06 defines the full semantic-search architecture (documents, segments, profiles, coverage, exact retrieval) but deliberately left the concrete default model unselected pending reproducible evaluation ("The concrete default local model is deliberately not selected yet"). That evaluation (`selectBundledProfile`, `packages/engine/src/semantic-selection.ts`) is not ready to ship. Rather than block every other piece of the semantic pipeline on it, this change introduces a provider abstraction (`ResolvedSemanticProvider`) with two concrete implementations and wires the whole path -- reconciler, query port, daemon, app config -- against that abstraction, so swapping in the evaluated model pack later is a provider swap, not a re-architecture.

## Decision

- **Pluggable provider; bundled default is a real open embedding model (updated 2026-08-13, superseding this doc's original interim hash default).** `packages/engine/src/semantic-provider.ts` exports `ResolvedSemanticProvider` (an `EmbeddingProfile` + a `SemanticRuntimeBinding`, produced together so their two identities can never drift apart). Three concrete providers exist: `createLocalNeuralProvider(options)` (`@urdira/embedding-local`, **the shipped default**), `createLocalHashProvider()` (`@urdira/engine`, demoted -- see below), and `createHttpEmbeddingProvider(options)` (`@urdira/engine`, opt-in, OpenAI-compatible). By USER DECISION, the bundled default moved off the ad-hoc hash embedder onto a real open model: `createLocalNeuralProvider` runs a transformers.js/ONNX `feature-extraction` pipeline (default model `Xenova/all-MiniLM-L6-v2`) entirely on-device, windowing long documents into non-overlapping `window_chars`-sized chunks (default 2000, capped at `max_windows` = 64), mean-pooling the per-window vectors, and L2-normalizing the result (`core:onnx-<model-sanitized>-<dims>` profile id, `core:onnx-local` runtime binding). The model lives in `<data_root>/models` (`cache_dir`) and is reused thereafter; `allow_download: false` restricts resolution to whatever is already cached, for fully offline operation -- and, per the configure-time provisioning update above, the daemon ALWAYS constructs this provider with `allow_download: false` (`packages/daemon/src/semantic-provider-runtime.ts`'s `buildSemanticProvider`); only `ensureLocalEmbeddingModel` (`@urdira/embedding-local`), called exclusively from a configure-time admin RPC, ever passes `allow_download: true`. Its vectors are deterministic per host, not guaranteed bit-identical across machines/ONNX builds -- an accepted property of running a real neural model locally (decision 06's "exact-build artifact" framing), unlike the hash provider's pure-integer-arithmetic bit-stability. `createLocalHashProvider` is **demoted, not removed**: it remains hermetic (pure-JS, offline, dependency-free, bit-stable) test/dev infrastructure, the explicit `URDIRA_EMBEDDINGS_PROVIDER=hash` escape hatch for environments that cannot run an ONNX model, and the fallback a bare `DaemonRuntime` (no app-level provider injected at all) still reaches for. Decision 06's evaluated, PREINSTALLED, data-only model pack (`selectBundledProfile`) remains the long-term endgame beyond even the open model here: that pack ships model weights as part of the release itself (no first-use download, no runtime dependency on the Hugging Face Hub being reachable), which `createLocalNeuralProvider` deliberately does not attempt -- it is a real step up from the interim hash embedder, not a replacement for decision 06's own destination. Any output-affecting change to either local provider's algorithm -- or the arrival of decision 06's pack -- mints a new `embedding_profile_id`/`runtime_binding_id` pair rather than mutating an existing one; the reconciler's profile-swap-close step (below) exists specifically to make that transition safe.
- **API provider is opt-in config, never a default.** `createHttpEmbeddingProvider` posts `{model, input: [text]}` to an operator-configured `endpoint` and expects an OpenAI-compatible `{data: [{embedding}]}` response. `apps/urdira/src/index.ts`'s `resolveSemanticDescriptor()` only builds an `{kind: "http", ...}` descriptor when `URDIRA_EMBEDDINGS_ENDPOINT` is set; `URDIRA_EMBEDDINGS_MODEL` and `URDIRA_EMBEDDINGS_DIMENSIONS` are then REQUIRED (both feed the profile's identity, per decision 06's "any behavior change capable of changing ... vector bytes ... creates a new profile identifier") and a missing/invalid value throws a clear startup `Error` naming the offending variable rather than silently building a descriptor with a nonsensical dimensionality. `URDIRA_EMBEDDINGS_API_KEY` is optional and is deliberately excluded from every digest the provider computes -- rotating a key must never force a profile swap and re-embed. Absent an endpoint, `resolveSemanticDescriptor()` checks the explicit `URDIRA_EMBEDDINGS_PROVIDER=hash` escape hatch next, then falls through to the bundled open-model default (`{kind: "neural", cache_dir: <data_root>/models, ...}`, with optional `URDIRA_LOCAL_EMBEDDINGS_MODEL`/`URDIRA_LOCAL_EMBEDDINGS_DTYPE` overrides). This function does PURE ENV PARSING ONLY -- no network, no ONNX load, no provider construction of any kind -- per the configure-time provisioning update above: constructing the actual provider (and, for `"neural"`, provisioning its model) is entirely `@urdira/daemon`'s own job now, run from the three configure-time admin RPCs, never from this app's startup.
- **Async, post-ready maintenance, mirroring the lexical reconciler.** `reconcileSemanticProjection` (`packages/engine/src/semantic-reconciler.ts`) runs after every successful scan/fork and on daemon startup for every already-ready workspace, submitted by `packages/daemon/src/runtime.ts`'s `submitSemanticMaintenance` (same per-workspace in-flight/pending coalescing, `"semantic"` scheduler pool, best-effort try/catch as `submitLexicalMaintenance`). It closes stale and profile-mismatched vector rows, embeds and writes vectors for visible non-binary artifact versions missing one under the current provider identity, and writes a completion marker only when the workspace's generation held still through the pass. Unlike the lexical reconciler, the marker is ALSO withheld whenever any document's embedding call itself failed (`failed > 0`) -- oversized/undecodable/empty skips are permanent, deterministic functions of content and would just reproduce on retry, but a `failed` row is explicitly meant to be retried, and writing the marker anyway would let the reconciler's own fast path skip re-attempting it forever.
- **Dedicated worker thread (updated 2026-08-13, supersedes "No dedicated worker thread, v1" below -- kept for history).** *Superseded text:* "`submitSemanticMaintenance` has no `semantic_thread` kill switch or thread-runner module, unlike `submitLexicalMaintenance`'s `lexical_thread`. This was true by construction for the ORIGINAL hash-embedder default (cheap, allocation-light per-document CPU work: a regex tokenize, two hashes, a 256-bucket accumulation) and remains true for an HTTP-backed provider (which spends most of its own time awaiting a network round trip, yielding on its own regardless); `reconcileSemanticProjection` also yields to the event loop once per document either way. The bundled OPEN-MODEL default (`createLocalNeuralProvider`) is a materially heavier per-document workload -- real ONNX inference, not a handful of hashes -- so this reasoning is weaker than it was for the doc's original hash default. It has not (yet) been observed to starve status RPCs at the same small/medium scale the lexical reconciler's own in-process path was measured at, so this remains the v1 choice, but moving semantic maintenance off-thread is now the more plausible near-term follow-up rather than a purely hypothetical one." *What actually happened next:* v1 shipped in-process as described above; a real installation then measured 5-20s of `core:query` latency against OTHER, unrelated workspaces while one workspace fleet-embedded under the ONNX default, entirely from main-thread tensor prep/inference contention -- the exact "more plausible near-term follow-up" this bullet already flagged. `packages/daemon/src/semantic-thread.ts` (`runSemanticReconcileInThread`) and `semantic-worker-thread.ts` now mirror `lexical-thread.ts`/`lexical-worker-thread.ts` exactly: a one-shot `node:worker_threads` worker per maintenance pass, `ABORT_GRACE_MS` (2s) cooperative-abort-then-terminate, resolved via `import.meta.resolve("@urdira/daemon")`. `DaemonRuntimeOptions.semantic_thread` (default ON, `URDIRA_SEMANTIC_THREAD` kill switch) gates it. Routing rule (`submitSemanticMaintenance`'s `semanticThreadEligible`, `runtime.ts`): the threaded path only ever runs when the active provider resolved from a plain `semantic_descriptor` -- an already-built `semantic_provider` INSTANCE cannot cross a `node:worker_threads` boundary (an in-process override always wins in-process, unconditionally), and a configured `semantic_runtime_hooks` test seam also forces in-process, since a worker always builds its provider through the REAL `buildSemanticProvider` and has no way to see injected fakes. `scheduleWorkspaceScan` aborts a workspace's in-flight threaded semantic run (`semanticThreadRuns`, mirroring `lexicalThreadRuns`) at the same point it aborts a threaded lexical run -- before the new scan is even admitted -- and the daemon resubmits semantic maintenance after that scan the same way it always has.

### Process-isolated neural execution (2026-08-15 amendment)

Neural query embeddings are served by a persistent child process and every
semantic maintenance pass runs in a one-shot child process. The daemon owns
only a `ResolvedSemanticProvider` proxy; ONNX construction and model access
remain in the child. `semantic_process`/`URDIRA_SEMANTIC_PROCESS` default to
enabled, with the thread-named settings retained as deprecated aliases.
- **Kill switch, matching every other maintenance job's convention.** `DaemonRuntimeOptions.semantic_index` (default ON) and `apps/urdira/src/index.ts`'s `URDIRA_SEMANTIC_INDEX` (`"0"`/`"false"`/`"off"`/`"no"` disables) mirror `lexical_index`/`URDIRA_LEXICAL_INDEX` exactly. Disabled, `core:search_semantic` always throws `core:semantic_index_unavailable` and `core:search_hybrid` always degrades to its lexical-only lane; no `semantic_index_state` row is ever written.
- **One provider per daemon process, resolved at start -- and, since this update, possibly activated ONCE more, later, without a restart.** `DaemonRuntime.start` resolves `semanticProvider` at most once at start (`options.semantic_provider` if injected; else, if `options.semantic_descriptor` is given, `buildSemanticProvider(descriptor)` -- forcing `allow_download: false` for a `"neural"` descriptor, so start NEVER touches the network; else `createLocalHashProvider()`; or `undefined` when the kill switch fired) and threads the SAME instance into every maintenance job and every workspace's query port (`CanonicalRecordQueryDataPort`'s `options.semantic`) for the rest of the process's lifetime -- UNLESS start's own build attempt failed (a `"neural"` descriptor whose model was not yet present offline), in which case `semanticProvider` stays `undefined` until a LATER configure-time admin RPC's `ensureAndActivateSemanticProvider` (`packages/daemon/src/runtime.ts`) successfully provisions and builds it -- at which point every cached per-workspace query engine is invalidated (see "Configure-time model provisioning" below) so the newly active provider serves the very next query, no restart. `DaemonRuntime`'s own internal `createLocalHashProvider()` default (no descriptor, no instance) is a bare-library fallback for callers with no opinion at all; the composed application (`apps/urdira`) never relies on it -- `defaultDaemonOptions` always resolves and injects an explicit `options.semantic_descriptor` (HTTP, hash, or the bundled open-model default) or explicitly disables semantic search. A query embedded under one provider identity is only ever compared against vectors written under that exact identity -- this is exactly why activation swaps the ONE process-wide instance atomically (a `let`, read directly at every call site) rather than resolving a provider per call.
- **Artifact-grain v1.** One vector per visible artifact version (`buildSemanticDocument`'s whole-file rendering), matching decision 06's dual-document-view architecture minus the entity-document half -- entity-grain documents are a later increment, not part of this wiring.
- **Async vector rows excluded from projection digests, extending decision 13.** `vector_projection_rows`, like `lexical_documents`/`lexical_trigrams`, are rewritten by an async post-ready pass, not written inside the publish transaction -- so a publish-time digest of them was stale the moment the reconciler's first post-publish rebuild landed. Decision 13 already made this exact argument for lexical rows and, in the same change, extended it to vector rows: `projectionSetDigestEntries` (`packages/storage/src/lifecycle.ts`) now covers only `graph`/`dependency`/`metric` (the projection kinds still written inside the publish transaction); `isKnownPreexistingVerifyGap` (`packages/engine/src/workspace-fork.ts`) excuses `storage:projection_set_digest_corrupt` for older snapshots unconditionally, and `StorageMaintenance.verify()`'s own "vector" integrity check keeps validating vector row *payload* integrity independently -- that check was never a publish-digest comparison and needed no change.
- **Exact-scan-only retrieval, per decision 06.** Both operations run `exactVectorScan` over every visible vector under the query's exact provider identity, capped at `SEMANTIC_CANDIDATE_CAP` (100) after structural filters (`paths`, `subject_types`) apply -- no approximate nearest-neighbor search, sampling, or bounded best-effort scan. `core:search_semantic` throws `core:semantic_index_unavailable` (never a silently narrowed answer) when no provider is configured, the query port lacks the semantic methods, or there are zero visible vectors and no current completion marker; `core:search_hybrid` degrades to its lexical-only lane in that same situation instead of failing outright, since it has a second lane to fall back on.
- **Configure-time model provisioning (USER DECISION, 2026-08-13).** The daemon and every embed path run strictly OFFLINE: the open local model is downloaded ONLY when urdira is CONFIGURED -- `core:workspace_add`, `core:workspace_configure`, and `core:configuration_set` -- never at daemon start, never on first query/index use, never during a scan. `SemanticProviderDescriptor` (PINNED, `packages/daemon/src/semantic-provider-runtime.ts`) is a plain, serializable `{kind: "neural"|"http"|"hash", ...}` description of which provider to build -- never a live instance, and never carrying `allow_download` (every daemon-owned `"neural"` build forces `allow_download: false` unconditionally). `DaemonRuntimeOptions.semantic_descriptor` is what `apps/urdira` threads through (built by `resolveSemanticDescriptor`, pure env parsing, no network); `DaemonRuntimeOptions.semantic_provider` (an already-built instance, mainly for tests) still wins for in-process use when both are given, but the descriptor is what a future worker thread would serialize across a thread boundary. Two functions in `semantic-provider-runtime.ts` do all the work: `buildSemanticProvider(descriptor)` (construct only, `allow_download: false` for `"neural"`) and `ensureSemanticAssets(descriptor)` (no-op for `"http"`/`"hash"`; for `"neural"`, `@urdira/embedding-local`'s `ensureLocalEmbeddingModel` -- attempt an offline construction first, classify `"present"`; on failure, attempt once more with `allow_download: true`, classify `"downloaded"` -- the ONE place in the whole system allowed to reach the network). Runtime behavior: at start, a `"neural"` descriptor's failed offline build logs a `console.warn` naming the exact remedy and leaves semantic effectively unavailable (`core:search_semantic` throws `core:semantic_index_unavailable`, `core:search_hybrid` degrades to its lexical-only lane, `submitSemanticMaintenance` no-ops) rather than crashing the daemon or downloading anything. Each of the three configure RPCs calls `ensureAndActivateSemanticProvider()` (a single coalesced in-flight promise) after ITS OWN request validation already succeeded; a provisioning failure `console.warn`s and that RPC continues normally -- a model download must never block structural indexing (decision 06's own framing, extended here). A provisioning SUCCESS while semantic was previously unavailable builds the provider, activates it as the ONE process-wide `semanticProvider`, and evicts every cached `CachedWorkspaceQueryEngine` (each one had captured `{semantic: undefined}` at its own construction time and cannot be reached into and changed after the fact) so the very next `core:query`/warm-up for ANY workspace builds a fresh query port against the newly active provider -- the fresh-install flow ("start the daemon with no model cached, `workspace-add` downloads it, the SAME daemon serves semantic with no restart") this update exists to support. `DaemonRuntimeOptions.semantic_runtime_hooks` (`{build?, ensure?}`) is a test-only seam overriding `buildSemanticProvider`/`ensureSemanticAssets` independently, so this whole activation sequence is covered hermetically (hash-provider-backed fakes, no network, no real model) in `tests/phase-daemon-indexing-integration.test.ts`.
- **Coverage and evaluation state.** `SemanticCoverageView.materialization_state` is `"complete"`/`"degraded"` when the marker is current (depending on whether every eligible artifact is covered), `"updating"` when the marker is stale or missing but the index is otherwise supported, and `"unavailable"` when it is not supported at all (no provider, unsupported port, or hybrid's fully-unindexed case). `OperationEvaluation.semantic_state` maps `"ready"`/`"partial"`/`"updating"`/`"unsupported"` from that same state one-to-one; `"failed"` is reserved for a future provider-level hard failure this port cannot yet distinguish from `"unavailable"`. `core:index_status`'s `semantic_materializations` view is populated from the daemon's own in-memory map, updated after every reconcile completion (including its fast path): `materialization_state` is `"complete"` once the marker lands, else `"degraded"` when the pass left any `failed` document, else `"updating"`; `coverage_status` is the stricter check that additionally requires zero oversized/undecodable/empty skips.

## Consequences

- `core:search_semantic`/`core:search_hybrid` answer real, incrementally maintained vector candidates through the full daemon IPC surface, with no code path left permanently unwired.
- Every vector row, every `semantic_index_state` marker, and every `EmbeddingProfile`/binding digest is keyed to a specific provider identity, so operators can run the bundled open-model local provider indefinitely, fall back to the hermetic hash provider, opt into an HTTP provider, or (later) receive decision 06's evaluated, preinstalled model pack, without any of those transitions silently mixing incomparable vector spaces -- the reconciler's profile-swap-close step retires every old-identity row as soon as the configured provider changes.
- Retrieval quality under the bundled default is now real learned semantic similarity from an open sentence-embedding model, not merely identifier/token overlap -- a genuine quality step up from this doc's original hash-embedder default, though still bounded by that model's own training distribution and the exact-window/mean-pool rendering `createLocalNeuralProvider` applies to whole files. The hash provider's identifier/token-overlap framing (documented in ITS OWN `agent_guidance` field) still applies wherever it is explicitly selected (`URDIRA_EMBEDDINGS_PROVIDER=hash`) or reached as a fallback.
- The bundled default now depends on a real model artifact being reachable, but ONLY at a configure-time admin RPC, never at daemon start or on an embed path -- `packages/daemon/src/runtime.ts`'s construction-failure handling (`console.warn` naming the configure remedy, semantic effectively unavailable rather than a hard crash) is the direct consequence: an operator who is offline with nothing cached yet gets an explicit, loud "run workspace-add/workspace-configure to provision it" rather than a silent, incomparable fallback vector space, or a network call the operator never asked for.
- Semantic maintenance now runs off the daemon's main thread by default (`semantic-thread.ts`, layered on top of `SemanticProviderDescriptor`), removing the fleet-embedding query-latency contention the ONNX default introduced -- no new persistence beyond `semantic_index_state` (already landed as a storage-slice prerequisite) and `vector_projection_rows`.

## Non-goals

- Selecting or shipping decision 06's evaluated neural model pack -- this change only makes that swap safe to do later, it does not do it.
- Entity-grain semantic documents, approximate/ANN retrieval, or per-language/namespace/kind structural filtering of the vector lane -- all explicitly out of scope for v1, matching decision 06's own exact-retrieval and lane-eligibility rules.
- Cross-machine or cross-provider vector reuse -- a provider swap (bundled to HTTP, or HTTP to a future pack) always re-embeds from scratch under the new identity, never migrates old vectors.
