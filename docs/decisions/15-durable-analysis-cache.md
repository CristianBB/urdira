# Durable Analysis Cache

Status: **Approved**
Last updated: 2026-08-13
Depends on: [JavaScript/TypeScript MVP](07-javascript-typescript-mvp.md), [Plugin upgrade relock](14-plugin-upgrade-relock.md)

## Decision objective

Stop every JavaScript/TypeScript worker from paying a full whole-project `analyzeProject` build (TypeScript program construction + type checking, ~42-47s on a 981-file workspace) on every scan, when a prior process already analyzed the identical inputs under the identical compiler/analyzer build.

## Context

`apps/urdira/src/index.ts`'s `buildJavascriptTypescriptPluginProvider` creates exactly one JS/TS worker per scan (`createJavascriptTypescriptThreadTransport` or `createJavascriptTypescriptWorker`, gated by `analysisThreadEnabled()`) and terminates it in a `finally` block once the scan finishes. `createJavascriptTypescriptWorker`'s in-memory `AnalysisCacheEntry` (`packages/plugin-javascript-typescript/src/worker.ts`) already avoids rebuilding within a single scan -- one whole-project build serves the `analyze_closure` call and every subsequent narrowed `analyze_artifact` call, via an exact key match or the `isSubsetOfCache` subset-reuse path. But that cache lives in the worker's own closure variables, which are destroyed the moment the worker (and, for the thread transport, the underlying `node:worker_threads` Worker) is terminated. Every NEW scan gets a brand new worker with an empty cache, so every one of the following pays a full rebuild even though the tree it's analyzing hasn't changed one byte since the last time this exact analysis ran: a daemon restart between two scans of the same workspace, a workspace removed and re-added, a rescan after `attemptWorkspaceFork` (decision 12) copies a donor workspace's tree into a new one, and a plugin-upgrade generation (decision 14) forced over a tree with zero source edits.

This durable cache closes that gap by persisting a finished `JsTsAnalysisResult` to disk, keyed purely by content, so a later worker -- in the same process or a different one entirely -- can load it back instead of re-running the checker.

## Decision

- **Key composition.** The durable key extends the existing in-memory `analysisCacheKey` (sorted `root_names` + per-file content hashes of the root files + `compiler_options`) with everything that must ALSO agree before a cross-process, cross-time entry is safe to trust: `format_version` (an explicit escape hatch for a future incompatible payload shape), `typescript_compiler_version` and `plugin_version` (`analyzeProject`'s output is only deterministic for a FIXED compiler and analyzer build -- an upgrade of either invalidates every existing entry by construction, which a version-free key would not catch), and the caller-supplied `analysis_digest`/`analysis_configuration_digest` (these don't affect `analyzeProject`'s own output, only `buildJavascriptTypescriptFactDelta`'s bookkeeping fields downstream, but folding them in means a configuration change that's supposed to be meaningful still mints a disjoint entry instead of two logically-different configurations quietly sharing one file-content-keyed entry). The whole thing is hashed with the existing `canonicalSha256`; only the hex half of its `sha256:<hex>` output becomes the filename stem, so cache filenames are plain hex.
- **Storage.** `<analysis_cache_dir>/<hex>.json.gz` -- gzip level 1 (fastest, not Node's default level 6) wrapping `{ format_version: 1, durable_key, analysis }`. Level 1 was chosen because this write is *awaited inside `invoke()`*, on the return path of every real build: gzip level 1 is several times faster than the default on a ~40MB analysis payload while still landing around 5x smaller than raw JSON, which keeps the awaited cost small relative to the build it's caching.
- **Awaited write, not fire-and-forget.** `thread-transport.ts`'s `terminate()` calls `node:worker_threads`' own `Worker.terminate()` directly -- a hard kill of the whole thread, not a message the in-thread worker gets to react to; the in-thread `createJavascriptTypescriptWorker`'s own `terminate` (which just clears in-memory state) is never invoked by it. `apps/urdira/src/index.ts`'s scan loop calls `worker.terminate()` in a `finally` block immediately after its last `invoke()` resolves. A fire-and-forget durable write started inside that last `invoke()` would therefore race the hard kill and could be silently truncated. The write is awaited to completion before `invoke()` returns, closing that race entirely.
- **Atomicity and corruption handling.** Every write goes to a per-write-unique temp file (`<hex>.json.gz.tmp-<pid>-<random>`) in the same directory, then an atomic `rename` over the final name -- a reader never observes a partially-written file. Since the durable key is a pure function of the analysis inputs, two workers racing to write the identical key always produce byte-identical content, so last-rename-wins between them is harmless. On read, `format_version`, the stored `durable_key` (recomputed and compared, not trusted blindly), and a minimal shape check on `analysis` (entities/relations/diagnostics are arrays, `dependency_closures` is a non-null object, `language`/`complete` have the right JS type) all have to pass; any failure -- missing file, a gunzip error on truncated/non-gzip bytes, a JSON parse error, or a shape mismatch -- is treated identically: best-effort `unlink` the bad file and fall through to a real build. Every fs/zlib/parse error the durable cache can produce is swallowed; it is a pure speedup and must never be able to fail a scan.
- **Prune policy.** After every successful write, entries beyond `analysis_cache_max_entries` (default 16) are evicted oldest-mtime-first, best-effort (swallowed on any error). 16 is generous enough to survive a handful of analyzer/compiler upgrades and a handful of genuinely distinct workspace trees without unbounded growth on disk, since every upgrade or distinct tree mints a disjoint key rather than overwriting an existing entry.
- **Placement: one shared directory, not per-workspace.** `defaultDaemonOptions` computes `analysis_cache_dir` as `<data_root>/analysis-cache/jsts`, one directory per daemon, not scoped to any single workspace. This is deliberate: the durable key carries nothing workspace-scoped (no `workspace_id`, no path outside the analyzed files themselves), so it is exactly what lets a freshly forked or re-added workspace over an already-analyzed tree hit an existing donor workspace's entry instead of rebuilding, the same way the in-memory cache already lets one scan's narrowed `analyze_artifact` calls reuse one `analyze_closure` build.
- **Kill switch.** `URDIRA_ANALYSIS_CACHE` (default on; `"0"`/`"false"`/`"off"`/`"no"` disables) follows the exact convention of `URDIRA_ANALYSIS_THREAD`/`URDIRA_LEXICAL_INDEX`/`URDIRA_WORKSPACE_FORK` -- a kill switch, not an opt-in, for ruling out a stale or corrupt on-disk entry when diagnosing an analysis discrepancy, or to skip the cache directory's disk usage entirely. Turning it off omits `analysis_cache_dir` from the worker descriptor entirely, which reproduces today's behavior byte-for-byte: no filesystem is ever touched by the durable-cache code path.
- **Test-only instrumentation.** `on_analysis_cache_load` mirrors the existing `on_analysis_build` hook -- fired on a durable disk hit instead of a real build. Both are function-typed, so both are excluded (via the same `Omit<..., "on_analysis_build" | "on_analysis_cache_load">` cast `worker-thread.ts` already used for the first one) from the descriptor fields that cross the `workerData` thread boundary; only the plain-data fields (`analysis_cache_dir`, `analysis_cache_max_entries`) do.

## Consequences

- A daemon restart, a workspace remove+re-add, a post-fork rescan, or a plugin-upgrade generation over an unchanged tree now costs roughly a gzip decompress + JSON parse of the cached analysis instead of a full whole-project TypeScript build -- the same order-of-magnitude win the in-memory cache already gave repeated calls within a single scan, now available across process boundaries.
- Disk usage under `<data_root>/analysis-cache/jsts` grows with the number of distinct (tree, compiler, analyzer, digest) combinations seen, bounded by `analysis_cache_max_entries` (default 16).
- A TypeScript compiler upgrade or an analyzer rebuild invalidates every existing durable entry at once (new `typescript_compiler_version`/`plugin_version`), which is intended: `analyzeProject`'s determinism guarantee only holds for a fixed build.

## Non-goals

- No cross-machine or cross-daemon sharing of the cache directory; it lives under one daemon's own `data_root` and is never synced or published anywhere.
- No change to the in-memory single-entry cache's own semantics (exact-key reuse, `isSubsetOfCache` subset reuse) -- the durable cache only participates on an in-memory miss, and a durable hit is installed into the in-memory cache exactly like a fresh build would be.
- No proactive warming: an entry is only ever written after a real build, never precomputed or backfilled for a tree that hasn't been scanned yet.
