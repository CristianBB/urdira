# Core Digest Field Contracts

Status: **Approved initial registry**  
Last updated: 2026-08-08  
Depends on: [Universal data model](../decisions/01-universal-data-model.md) and [Urdira Canonical Encoding](urdira-canonical-encoding.md)

## Purpose and notation

This registry assigns every core model field of logical type `Digest` to exactly one computation recipe (`C`) or digest reference (`R`). A computed field hashes the UCE envelope. A reference copies the exact terminal recipe output and verifies it without rehashing.

All definitions below have `definition_revision: 1`, `schema_version: 1`, and `lifecycle_state: active`. Computation recipes use `recipe_version: 1`, UCE v1, and SHA-256. `schema_id@version` and `comparator_id@version` are compact pair notation: `@1` is never part of the identifier and never denotes a floating alias.

Notation:

- `{a, b, c}` is a closed record payload with exactly those fields and their target-schema logical types.
- A `?` suffix inside a payload field list denotes a schema-optional field whose exact presence rule is stated in that row; the suffix is notation and not part of the field name.
- `value(path)` is a direct binding from the target.
- `input(Type)` is a schema-validated `verified_input` supplied to `DigestComputationContext`; a named schema always uses the explicit `schema_id@version` pair notation above.
- `digest(recipe, locator)` is a `referenced_digest` binding to the exact recipe version.
- `ordered_set(Type, comparator)` is the complete duplicate-free set under the exact named immutable `comparator_id@version`.
- Every omitted optional target field is absent in the payload; present optional values retain presence. No default is inferred.

## Verified-input terminal recipes

These recipes define authoritative terminal digests for assets whose complete bytes or canonical manifests are supplied as verified input rather than selected from ordinary holder-model fields. A holder field may compute the terminal recipe directly, as listed under computed fields, or copy its exact output through a `DigestReferenceDefinition`; the two modes are never interchangeable for one target field.

The manifest and configuration schemas above are canonical schemas in the registry even when their values are retained in an asset store rather than exposed to agents.

Every distinct value in the Domain column of this file is also the authoritative initial core `DigestDomainDefinition`. Its `digest_domain` is that value; `description` is exactly "Digest space governed by recipes: " followed by the lexicographically sorted comma-separated recipe identifiers that use the domain. Common initial definition and lifecycle defaults apply. This deterministic construction prevents an unmodeled or multiply owned domain from appearing in a recipe.

Every verified-input terminal row also defines one initial core `ExternalVerificationContractDefinition`. Its identifier is the recipe identifier with the final `_digest` replaced by `_verification_contract`; `contract_version` is `1`; its verified-input schema is the row's payload schema; its terminal recipe is the row's recipe at version `1`; and `verification_semantics` is the complete exact capture, selection, and exclusion sentence in that row. A row using raw `Bytes` selects the registered `core:Bytes@1` schema. These derived identifiers are retained by registry snapshots and are used by every `external_asset` reference below.

For a computed verified-input field whose digest is also the only collision-safe asset address, the claimed target digest may locate a candidate input object but is never evidence of correctness. Urdira first validates every non-digest coordinate stated by the row, validates the complete input schema, recomputes the terminal recipe, and accepts only byte-for-byte equality. This rule permits two distributions that reuse a provider revision or package version to remain distinct without making selection ambiguous.

## Digest reference contracts

Each row is one `DigestReferenceDefinition`. For every row, `digest_reference_id` is `core:` followed by the target model and complete field path converted to lowercase snake case and suffixed `_reference`; source recipe version is `1`; and target schema/version are the exact initial pair denoted by the target model. The snake-case conversion inserts a boundary before an uppercase ASCII letter following a lowercase letter or digit, and before the final uppercase letter of a run followed by a lowercase letter; it then lowercases ASCII and replaces every remaining non-alphanumeric run with one underscore. `model` references use the listed locator. `external_asset` references use the verifier contract deterministically derived from the named terminal recipe under the rule above, at contract version `1`. These construction rules are part of the registry and produce no floating identifiers.

## Validation invariants

- A schema activation scan must find exactly one row in this registry for every core `Digest` field and no row for a non-`Digest` field.
- Optional digest fields have a contract even when absent. Presence constraints remain owned by the target schema.
- Fields ending in `_hash` in legacy approved model names are still logical `Digest` values; new model fields should prefer `_digest`.
- A reference value must equal its authoritative terminal digest byte for byte, including the algorithm tag.
