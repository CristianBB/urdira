## 3. Lexical/semantic sidecars

`workspace-v4-lexical.sql` (`lexical_documents`, `lexical_fts`,
`lexical_index_state`) and `workspace-v4-semantic.sql` (`vector_shards`,
`vector_projection_rows`, `semantic_index_state`) keep every column
byte-identical to v3 per the task brief ("keep columns identical to v3 for
now... only the file location changes"), including `workspace_id` on every
row even though the sidecar files are already scoped to one workspace.
One necessary deviation, forced by the file split rather than chosen: the
`FOREIGN KEY` from `lexical_documents`/`vector_projection_rows` to
`artifact_versions` is dropped, because `artifact_versions` now lives in a
different SQLite file and SQLite cannot enforce a cross-file foreign key
without `ATTACH`. This is called out inline in both `.sql` files.
`vector_projection_document_ref_idx` stays un-created here for the same
reason it is absent from v3's inline schema (see that table's v3 comment) --
`initializeSchema` runs unconditionally on open, before
`ensureWorkspaceSchemaCompatibility` guarantees the `document_grain`/
`document_ref` columns exist; a v4 equivalent of that ALTER/index step is not
in scope for P2-1.

## 4. Generator and Rust mirror

`scripts/generate-workspace-v4-sql.mjs` reads the three `.sql` authorities
and writes `WORKSPACE_V4_SCHEMA`/`WORKSPACE_V4_LEXICAL_SCHEMA`/
`WORKSPACE_V4_SEMANTIC_SCHEMA` as literal string constants to both
`packages/storage/src/workspace-v4-sql.generated.ts` and
`crates/urdira-indexing-core/src/workspace_v4_sql.rs`. This differs from the
v3 generator, which only mirrors a SHA-256 *digest* into Rust: v3's Rust side
never creates the workspace schema itself (TypeScript does, at open), so a
digest is enough to detect drift. v4's Rust cold/incremental pipeline is
meant to create `workspace.sqlite` itself (plan §9, "Rust comprueba lo
mismo"), so Rust needs the literal schema text, not just a digest.
`pnpm generate:workspace-sql` now runs the v3 generator followed by the v4
generator (`package.json`).

Byte-for-byte equality is asserted twice, per file, in
`tests/workspace-v4-sql.test.ts` (TypeScript constant vs. the `.sql` file
via `readFileSync`, and the Rust constant -- extracted from its
`pub const ... = "...";` literal and `JSON.parse`d, since the generator wrote
it with `JSON.stringify` -- vs. the same `.sql` file) and once more from the
Rust side in `crates/urdira-indexing-core/src/lib.rs`'s new
`workspace_v4_schema_matches_sql_authority` test, which compares the Rust
constants to `include_str!` of the same three `.sql` files. `cargo test -p
urdira-indexing-core workspace_v4` passes (1 test).

## 5. `schema.ts` / `storage.ts` additions

- `WORKSPACE_V4_INDEX_CONTRACT = 0x34` -- distinct from v3's `0x33` so a v3
  database can never be misread as v4 (or vice versa).
- `ensureWorkspaceSchemaCompatibilityV4(database)` -- mirrors
  `ensureWorkspaceSchemaCompatibility`'s stamp-on-empty/reject-on-mismatch
  logic, scoped to the v4 contract byte. Unlike the v3 function it has no
  legacy-preview repair steps (v4 has no prior shipped shape to be backward
  compatible with). **Not called from any open path.**
- `STRUCTURAL_STORE_META_KEY = "structural_store"` + `readStructuralStore`/
  `writeStructuralStore` -- canonical-encoded (`encodeCanonical`/
  `decodeCanonical`, matching `bindWorkspaceIdentity`'s existing pattern) so
  the eventual daemon can record and read back which structural-store engine
  (`"native"` vs. `"sqlite"`, plan Path N vs. Path S) a workspace was created
  with.
- `V4_IDENTITY_FORMAT = 3` in `storage.ts`, next to `CURRENT_IDENTITY_FORMAT`
  (still `2`). Not read or written anywhere yet -- `CURRENT_IDENTITY_FORMAT`
  stays the v3 runtime's value until P4.
- `WorkspaceDatabase.openSidecar(kind: "lexical" | "semantic")` -- opens (and
  creates on first use) `<workspace-basename>.<kind>.sqlite` next to the
  workspace's catalog file, applies the matching sidecar schema via
  `initializeSchema`, and caches the connection per kind for the handle's
  lifetime; `close()` now closes and clears any opened sidecars alongside the
  main database. **Naming-convention assumption**: v3's on-disk layout today
  is a flat `<data_root>/workspaces/<safeId>.sqlite` file (see
  `defaultWorkspacePath` in `storage.ts`), not yet the per-workspace
  *directory* the plan's §1 diagram sketches (`<data_root>/workspaces/<ws>/`
  containing `workspace.sqlite`, `structural/`, `lexical.sqlite`, etc.).
  Since that directory restructuring is not part of P2-1, `openSidecar` and
  `recreateOutdatedWorkspaceDatabase` (below) both derive sidecar names as
  siblings of the existing flat file using its own basename as a prefix
  (`<safeId>.lexical.sqlite`, `<safeId>.structural/`), so nothing here needs
  to change again if/when a later phase introduces the per-workspace
  directory -- only the base directory each sibling sits in would move.
  Every writer-mode `openSqliteDatabase` connection already applies WAL +
  `synchronous = FULL` + `busy_timeout`/`foreign_keys` pragmas
  (`sqlite.ts`'s worker `openDatabase`), so `openSidecar` needs no separate
  pragma step to match "the same pragmas as `sqlite.ts` writers".

## 6. `recreateOutdatedWorkspaceDatabase` / `isOutdatedWorkspaceError`

`packages/storage/src/recreate-outdated.ts`. Given `{ rootDir, workspaceId,
databasePath, reason, logger?, now? }`, it:
1. Creates `<name>.v3.stale-<timestamp>/` next to the database (same
   directory as `databasePath`; `<name>` is the basename with `.sqlite`
   stripped; timestamp is `new Date(now()).toISOString()` with `:`/`.`
   replaced by `-` for filesystem safety).
2. Moves (renames, never deletes) whatever of the following exist:
   `<name>.sqlite`, `-wal`, `-shm`, `.urdira-writer.lock`, the sibling
   `<name>.structural` directory, and `<name>.lexical.sqlite`/
   `<name>.semantic.sqlite` with their own `-wal`/`-shm` siblings -- matching
   the sidecar naming convention `openSidecar` uses (§5). Missing optional
   siblings are silently skipped.
3. Logs exactly one line (default: one `process.stderr.write`, overridable
   via `logger`) naming the workspace, the relative database path, the
   reason, the destination directory, and the remediation ("re-register or
   rescan... to reindex from scratch").
4. Returns `{ staleDirectory, movedPaths }`.

`isOutdatedWorkspaceError(error)` recognizes `error.code` in
`{"core:index_contract_unsupported", "storage:workspace_format_outdated"}`
(the two error codes `ensureWorkspaceSchemaCompatibility(V4)` and
`ensureIdentityFormat` raise today). **Not wired into the daemon's open
path** -- P4 calls this from the daemon's handling of those two error codes.

Unit tests (`tests/recreate-outdated.test.ts`) cover: every sibling present
and moved, an optional sibling absent (must not fail the move), the log
line's content, and both/neither/an unrelated error code for the predicate.
Uses a real temp directory (`mkdtemp`/`node:fs/promises`), not a mock
filesystem, per the existing test suite's convention (`tests/cas-stream.test.ts`
et al.).

## 8. What is deliberately NOT done here (future phases)

- Nothing is wired into `openWorkspace`, `registerWorkspaceSerialized`, or
  any daemon open path. Selecting v4 for a workspace, actually creating
  `structural/`, and routing queries through a native/SQLite
  `CanonicalQuerySnapshotPort` are P2-2 through P2-7 and P4.
- `recreateOutdatedWorkspaceDatabase` is not called from the daemon's
  `core:index_contract_unsupported`/`storage:workspace_format_outdated`
  handling yet (P4, per plan §9).
- The per-workspace *directory* layout the plan's §1 diagram sketches (as
  opposed to today's flat `<safeId>.sqlite` file with sibling-named
  sidecars) is not introduced here; see the naming-convention note in §5.
- `ensureWorkspaceSchemaCompatibilityV4` has no equivalent of v3's
  `vector_projection_document_ref_idx` late-index-creation step; that would
  need to move into whatever ALTER/backfill step a v4 workspace's first real
  open eventually runs.
